# Reference Price Selection for an On-Chain Arbitrage-Capture Hook

Technical appendix to **Backdraft** · Uniswap v3 ETH/USDC, Ethereum mainnet
UHI10 · HK-UHI10-1088

Every figure here is generated by the scripts in
[backdraft-python-scripts](https://github.com/mansi0xc/backdraft-python-scripts) and
committed to its `out/` directory. Nothing is transcribed. The commands that produce
each table are given at the end.

---

## 1. The question this answers

Backdraft charges a surcharge on swaps that close a price gap. To do that it must
decide, on every swap, whether the pool is currently mispriced and by how much. That
requires a **reference price** — some number the hook can read on-chain and treat as
what the asset is actually worth right now.

Every arbitrage-capture hook needs one, and each existing implementation picks
differently: Pyth (Detox), Chainlink CRE (ArbHook), a second connected pool (WTH),
Scroll's L1SLOAD (Read-on-L1), external v2/v3 pools (arb-hook). None that we found
publishes how wrong its reference actually is. Without that number a surcharge
threshold cannot be set honestly — too low and the hook charges traders for its own
measurement noise, too high and it misses the dislocations it exists to capture.

So we measured candidate on-chain references against centralised-exchange ground truth
across three mainnet windows and derived the design from the results.

### Why a centralised exchange is the right benchmark here

For most oracle work, CEX price is a contestable proxy for some abstract true value.
For Backdraft it is not a proxy at all: the arbitrage being priced is literally executed
against a centralised venue. When the pool goes stale an arbitrageur buys from the pool
and sells on Binance, and their profit is (Binance price − pool price) × size. The
question the reference must answer is not "what is ETH worth" but "is there a gap
someone can actually trade against, and how large". Binance is the deepest ETH spot
venue, so it is the most likely counterparty, not a compromise.

## 2. What each metric means

All errors are in basis points. On Uniswap v3 one tick equals one basis point to within
0.01%, so tick error and bps error are interchangeable.

| Metric | Definition | Why it matters here |
|---|---|---|
| Mean error | Average absolute distance from CEX price over every block | Ranks methods. Not the parameter that sets thresholds. |
| Median error | The typical error | Less distorted by spikes. Mean ≫ median means a heavy tail. |
| p95 error | Exceeded on 5% of blocks | The practical detection floor. Gaps smaller than p95 are indistinguishable from noise. |
| Max error | The single worst block in the window | Sets what the hook may charge for. If the reference can be wrong by X bps, charging on a gap smaller than X charges someone for our error. |
| Lag | Blocks behind CEX, from cross-correlating changes in the estimate against changes in truth | A slow reference detects dislocations after the arbitrageur has taken them. |
| Coverage | Fraction of blocks producing a usable value | Below 100% means the method refuses to answer. |
| Liquidity share | In-range liquidity as a fraction of the pair's total | Proxy for how expensive a source is to push. |
| `min_weight` | Share of pair liquidity an attacker must control to move the result | Manipulation resistance stated as a cost. Higher is safer. |

**A note on "max".** Every max in this document is a *sample* maximum over a finite
window on one pair. It is an observed value, not an upper bound, and any threshold
derived from it inherits that status.

## 3. Method

Uniswap v3 `Swap` events were pulled for all four ETH/USDC fee tiers. Each event carries
the post-swap tick and in-range liquidity, so a per-block price series follows by
forward-filling between swaps — a pool's price changes only when someone trades. Binance
closes provide ground truth, joined backward onto block timestamps. Pool addresses are
resolved from the v3 factory at runtime rather than hardcoded, and the arithmetic is
covered by a self-test suite: tick↔price round-trips, event decoding with negative
values, and the weighted-median breakpoint verified to hold at exactly 50.0% attacker
weight and flip at 50.2%.

### The three windows

| Blocks | Dates | Blocks | Ground truth | Window high–low |
|---|---|---|---|---|
| 25527155–25534325 | 14 Jul 2026 | 7,166 | ETHUSDC 1m | 7.00% |
| 25598870–25606053 | 24 Jul 2026 | 7,179 | ETHUSDC 1m | 3.37% |
| 25785425–25799780 | 19–21 Aug 2026 | 14,356 | ETHUSDC **1s** | 23.85% |

Windows are described by the measured high–low range of the ground-truth series rather
than by an adjective, because an earlier draft's adjectives were wrong and the number
cannot be. None of the three is genuinely calm; the two July windows are quieter, not
quiet. Claims of the form "holds across calm and volatile regimes" are therefore not
supported here and are not made.

The August window uses 1-second candles because blocks arrive every ~12 s and 1-minute
truth is up to 60 s stale, which penalises fast references specifically.

### Swaps per source

| Pool | Fee | 14 Jul | 24 Jul | 19–21 Aug | Liquidity share (Aug) |
|---|---|---|---|---|---|
| `v3_001` | 0.01% | 18,066 | 14,076 | 46,344 | 10.0% |

The cheapest tier holds a tenth of the liquidity and carries three times the trade count
of the deepest. That inversion is the whole result.

### Single-source accuracy, all three windows

arbitrageurs' first stop, so it is corrected more often.

**Price freshness is produced by trade frequency, not by depth.**

The margin between first and second is 0.70–0.92 bps, near the precision limit of the
instrument. Three windows agree on the sign; we do not claim the magnitude.

## 5. Does combining sources help?

Standard oracle practice aggregates several sources weighted by depth. Every subset of
the four pools was evaluated as a liquidity-weighted median. August window:

| Sources | Mean err | p95 | Liq. share | `min_weight` |
|---|---|---|---|---|
| `v3_001` alone | **3.482** | 11.254 | 0.100 | 0.050 |
| `v3_001 + v3_100` | 3.482 | 11.254 | 0.102 | 0.051 |
| `v3_001 + v3_005` | 4.177 | 9.882 | 0.881 | 0.441 |
| `v3_005 + v3_030` | 4.177 | 9.882 | 0.898 | 0.449 |
| all four | 4.177 | 9.882 | 1.000 | 0.500 |

Every combination containing `v3_005` returns exactly `v3_005`'s error, to three
decimals, in all three windows. This is forced, not coincidental: a liquidity-weighted
median returns the value held by whichever source controls >50% of the weight, and the
deep pool always does. Adding the deep pool to the fresh one makes the reference ~20%
worse.

**Accuracy gained by going multi-source: 0.000 bps.**

What aggregation does buy is attack cost: `min_weight` rises from 0.050 to 0.500, a 10×
increase, at 3–4× the read cost. The trade is entirely accuracy-for-resistance.
Backdraft buys that resistance more cheaply from a divergence signal instead (§7).

**The corollary no hook we surveyed draws:** because the freshest source is not the
deepest, weighting by liquidity systematically selects the *staler* price. On this pair
standard oracle practice points the wrong way.

## 6. Why a pool cannot reference itself

Backdraft's first design used a damped EMA of the pool's own tick history — no external
dependency, no extra reads. It fails structurally, not by tuning.

When the external market moves and the pool goes stale, the pool's own history reports
no deviation, because it *is* the stale price. Deviation-from-own-recent-price and
deviation-from-truth are different quantities, and only the first is observable without
an external source.

Worse: the arbitrageur correcting the pool moves its tick *away* from the EMA. Under
Backdraft's contribution ledger that registers as gap-widening, so the hook would credit
a rebate to the arbitrageur extracting from its own LPs.

| Reference | 14 Jul | 24 Jul | 19–21 Aug | vs shipped (Aug) |
|---|---|---|---|---|
| `shipped_fast_spot_raw` | 4.15 | 2.31 | 3.48 | — |
| `own_pool_ema` | 52.56 | 33.52 | 58.23 | **16.7×** |
| `own_pool_ema`, 30% flow | — | — | 72.78 | 20.9× |
| `own_pool_ema`, 10% flow | — | — | 105.57 | 30.3× |

The flow-rate variants model a newly launched pool where most blocks contain no swap at
all. The proxy is the 1.00% tier, the thinnest available, which is generous: it borrows
a real pool's price path, whereas a genuinely new pool would also have wider spreads and
worse price discovery. These are a lower bound on how bad it gets.

## 7. TWAP, and what replaced the freeze

A time-weighted average is the standard defence against price manipulation: a flash loan
can move spot within one block but cannot move a 30-minute average. As a *reference* it
fails badly — accuracy degrades monotonically with window length. August window:

| TWAP window | Mean err | p95 err |
|---|---|---|
| 60 s | 4.63 | 11.74 |
| 120 s | 6.04 | 15.92 |
| 300 s | 9.41 | 26.21 |
| 600 s | 13.30 | 39.69 |
| 900 s | 16.31 | 48.78 |
| 1800 s | 25.18 | 76.94 |
| 3600 s | 40.32 | 125.97 |
| 7200 s | 60.32 | 338.32 |

The conclusion is not "use a short TWAP" but **"do not use a TWAP as the reference"**.
Its lag is a defect when predicting truth — and precisely the property that makes it a
good manipulation *detector*. So it is used as a signal, never as the price.

### The divergence signal

The hook computes, on every swap, the worse of two disagreements:

```
divergence = max( |deep spot − deep 30-min TWAP| ,   ← the deep pool being pushed
                  |fast spot − deep spot|         )  ← the fast pool being pushed
```

Taking the max means an attacker cannot hide by splitting the push across both.
Measured, August window:

| | ticks |
|---|---|
| mean | 25.04 |
| p95 | 78.16 |
| p99 | 247.04 |
| max | 642.27 |
| share of blocks above 50 | 10.06% |

### What changed, and why

The original design **froze** on divergence above 50 ticks: no credit, no surcharge, no
capture. On its own terms that looked excellent —

| | Unguarded | Frozen | Change |
|---|---|---|---|
| Mean error | 4.18 | 3.50 | −16% |
| p95 error | 9.88 | 8.15 | −18% |
| Max error | 228.65 | 57.97 | **−75%** |
| Coverage | 100% | 89.9% | −10.1% |

Worst-case error falls 4× for 10% downtime. The freeze rate also self-calibrates without
tuning — 1.67% of blocks on 24 Jul, 3.89% on 14 Jul, 10.06% on 19–21 Aug — engaging when
markets move and staying out of the way otherwise.

**That self-calibration is the problem.** The blocks where spot and TWAP disagree are
exactly the blocks where a fast exogenous move is happening. A guard that trips on
divergence trips during the events the hook exists to capture. §8 measures what that
costs, and the answer is why the shipped design prices divergence instead: the surcharge
rate is multiplied by a graduated factor as divergence rises, bounded by a ceiling, and
the reference is withheld only at an absurdity backstop far above the tolerance.

An unreliable reference should produce a *more expensive* charge, not an absent one.

## 8. Where the dislocation value actually is

Block shares do not answer the question that matters, because volatility clusters: the
blocks a guard would freeze are not a random 10% of blocks. Every swap in a target pool
is bucketed by what `beforeSwap` would have seen — pre-swap pool tick against the 0.01%
reference at that log position — and weighted by `|gap| × swap notional`, which is the
surcharge base.

Three stand-in target pools, August window, by **dollar-weighted share**:

| Target pool | Swaps | Blind (\|gap\| ≤ 65) | Capturable at 1.00× | In divergent blocks |
|---|---|---|---|---|
| `v3_100` (thin) | 114 | 0.43% | 8.83% | **90.73%** |
| `v3_030` (mid) | 1,154 | 63.30% | 0.00% | **36.70%** |
| `v3_005` (busy) | 14,868 | 60.92% | 0.45% | **38.63%** |

**Finding 1 — the blind spot is a function of flow, not of the threshold.** On a thin
pool almost all dislocation value clears 65 ticks; on a busy pool most of it never does.
Backdraft is economically meaningful on **thin pools of major pairs** — a new v4 pool
bootstrapping against a deep v3 incumbent — and close to irrelevant on a pool that is
already the price-setter. That is a positioning statement, not a defect.

**Finding 2 — a boolean guard would have switched the hook off on most of the value it
exists to capture.** Pricing divergence instead of freezing on it moves that entire
column back into scope, at a raised multiplier:

| Target pool | Boolean guard | Shipped |
|---|---|---|
| `v3_100` | 8.83% | **99.57%** |
| `v3_030` | 0.00% | **36.70%** |
| `v3_005` | 0.45% | **39.08%** |

This is the strongest single argument in the project for pricing divergence, and it was
computed *after* the change rather than before it. An earlier draft of this appendix
predicted the direction and declined to guess the size. The size is an order of
magnitude.

### The same measurement on the quieter windows

The August table is one window. Across all three, the shipped capturable share is:

| Target pool | 14 Jul | 24 Jul | 19–21 Aug |
|---|---|---|---|
| `v3_100` (thin) | 99.97% | 99.98% | 99.57% |
| `v3_005` (busy) | 65.20% | 41.13% | 39.08% |
| `v3_030` (mid) | **0.00%** | **0.52%** | 36.70% |

The thin-pool result is the robust one: 99%+ in every window. The mid-pool result is
not — on 14 Jul, 100% of its dislocation value sat under 65 ticks and the hook would
have captured nothing at all. Quoting only the August column would overstate the
mechanism by two orders of magnitude on that pool.

**Caveats that belong with these numbers.** `n = 114` swaps on the thin pool in the
August window and 48 on 14 Jul, so its column is indicative rather than a finding. The
TWAP here is a 150-block rolling mean of deep-pool swaps rather than a v3 `observe()`
result. And these are stand-in pools, not Backdraft pools — no v4 pool with this hook
has traded.

## 9. What it costs to hide a gap

Backdraft prices the reference from the spot tick of the thinnest of the four pools.
That is the accuracy result from §4, and it is also an attack surface: pushing the fast
pool toward the v4 pool's price shrinks the apparent gap below the threshold, no gap
opens, and the arbitrageur closes the whole dislocation surcharge-free.

The model computes the round-trip swap fees plus gas to move the 0.01% pool N ticks and
unwind, against the surcharge avoided, and reports the arbitrage notional at which the
attack breaks even. At median in-range liquidity:

| Window | Break-even at a 66-tick gap | at 100 ticks |
|---|---|---|
| 14 Jul | $18,193 | $27,165 |
| 24 Jul | $18,097 | $24,698 |
| 19–21 Aug | $22,668 | $39,492 |

**The attack pays.** Break-even sits at $18k–$40k of arbitrage notional, well inside
ordinary trade sizes on this pair. The graduated divergence multiplier does not deter
it, because a *successful* mask means no gap opens and there is nothing to multiply.

What the model does not include, stated so the number is not read as more precise than
it is: constant liquidity across the pushed range (real v3 crosses initialised ticks;
near spot on a major pair liquidity is usually deepest, so the real push tends to be
*cheaper* than modelled, making this an upper bound generous to the defence); competing
searchers during the push; non-atomic unwind risk. No attack was executed against a live
pool.

Gap **freezing** and gap **masking** are the same attack seen from two sides, and no
single divergence tolerance closes both — tightening it to stop masking widens the
freeze window, and vice versa. A truncated reference, bounding how far the reference may
move per block, is the direction that addresses the tail without that tradeoff. It is
measured in the repository and is not implemented.

## 10. The reference Backdraft ships

| Role | Source | Why |
|---|---|---|
| **Reference price** | `v3` 0.01% pool, current tick | Most-traded, therefore freshest. Best accuracy in all three windows (§4). |
| **Divergence signal** | `v3` 0.05% pool: spot vs its own 30-min TWAP, and fast vs deep | Deepest source, hardest to push. Taking the max of both closes the split-push route (§7). |
| **Failure mode** | Price the divergence; withhold only at an absurdity backstop | A guard that switches off during fast moves switches off during the events the hook exists for (§8). |

The 0.01% pool is fresh but thin: 5.0% of pair liquidity would corrupt it. The 0.05%
pool is stale but deep. Using the fast pool alone is accurate and attackable; using the
deep pool alone is safe and ~20% less accurate; combining them by liquidity weight gives
the deep pool's accuracy at 3× the read cost. Taking the price from the fast source and
the sanity check from the deep source is the only combination with both properties.

### Parameters this fixes

| Parameter | Value | Derived from |
|---|---|---|
| `gapThresholdTicks` | 65 | Above the *frozen* reference's sample max of 57.97 bps. See the caveat below. |
| `guardMaxDevTicks` | 50 | Divergence tolerance. Yields the freeze rates in §7 under the old design; under the shipped design it is where the multiplier begins to rise. |
| Practical detection floor | ~11 bps | p95 error of the shipped reference. Smaller gaps are inside measurement noise. |
| Reads per swap | 3 external calls | Two `slot0`, one `observe()`. Measured at 66k–77k gas against mainnet. |

**The threshold does not cover the shipped reference's worst case.** 65 ticks was
derived against the *frozen* reference's sample max of 57.97 bps. The reference that
ships is never withheld, and its sample max is **228.65 bps** — 3.5× the threshold, on
~0.19% of blocks in the August window. On those blocks a gap opens that should not, and
the divergence multiplier makes the mischarge *larger*, not smaller. This is bounded by
the surcharge cap, not eliminated. It is the largest open item in the design.

### Verified on mainnet

The reference reader is exercised against the live v3 pools it names, at a pinned block
and at head (`test/fork/Replay.t.sol`, 9 assertions). Each test recomputes the reader's
output from raw `slot0` and `observe` calls and asserts equality, so a wrong pool, a
misparsed tuple, a dropped truncation correction or an inverted divergence signal fails
there rather than in production. Observed across three runs: divergence 4–36 ticks,
`getRefTick` 66,175–76,564 gas.

## 11. Relation to prior work

The fee-tier ordering is not novel and is not claimed. Alexander, Chen, Deng & Fu (2025),
*Journal of Futures Markets* 45(8), 1023–1048, report from three years of minute-level
data that v3 prices in 0.05% pools tend to lead those in v2 and 0.30% pools, and that
the 0.01% pool is marginally more efficient than the 0.05% pool. This measurement
independently reproduces their ordering with a different metric on a different pair.
They exclude Binance for gaps in long-run coverage; at a two-day timescale coverage is
complete.

Reading external pools from a hook is not novel either: Detox uses Pyth, ArbHook uses
Chainlink CRE, WTH uses a second connected pool, Read-on-L1 uses Scroll's L1SLOAD,
`sterlingcrispin/arb-hook` reads external v2/v3 pools. Uniswap Labs' own Truncated
Oracle hook caps per-block tick movement to resist manipulation.

What we believe is unclaimed:

| | Prior work | This work |
|---|---|---|
| Source selection | By depth, or by whatever feed is available | By measured accuracy against CEX |
| Reference vs guard | Same source for both | Split: fast source prices, deep source guards |
| Threshold setting | Chosen | Derived from measured error, with the shortfall stated |
| Divergence handling | Freeze, or ignore | Priced, with the cost of freezing measured (§8) |
| Published error | None found | Three windows, bps against CEX |

## 12. Limitations

- **One pair, one chain, three windows.** ETH/USDC on Ethereum mainnet, two days in July
  and two in August. The trade-frequency result should hold wherever a cheap tier
  attracts arbitrage flow, but that is an expectation, not a measurement.
- **The margin on the headline ordering is small.** 0.70–0.92 bps, near instrument
  precision. Three windows agree on the sign; the magnitude is not claimed.
- **Every "max" is a sample max.** An observed value over a finite window, not an upper
  bound. Deployments should monitor realised reference error and version the threshold
  as the observed tail grows.
- **The threshold does not cover the shipped reference's tail.** §10.
- **Ground truth is a single venue.** Other exchanges differ by a few bps — the same
  order as the difference between the two leading methods.
- **Block timestamps are interpolated** at ~12.04 s/block between window endpoints
  rather than fetched per block. Adequate for candle joins, not for sub-block work.
- **Manipulation-resistance figures are analytic.** `min_weight` follows from the
  weighted-median breakpoint; the §9 cost model is a model. No attack was executed.
- **The bucket-value study uses stand-in pools.** No v4 pool running this hook has
  traded, so §8 measures what the hook *would* have seen, not what it saw.

## 13. Reproducing

```bash
git clone https://github.com/mansi0xc/backdraft-python-scripts
cd backdraft-python-scripts && pip install -r requirements.txt

# arithmetic, no network
python3 selftest.py --selftest

# §4–§7 tables, one window at a time
START_BLOCK=25785425 END_BLOCK=25799780 BINANCE_INTERVAL=1s python3 analyze.py
START_BLOCK=25527155 END_BLOCK=25534325 python3 analyze.py
START_BLOCK=25598870 END_BLOCK=25606053 python3 analyze.py

# §8, per target pool
python3 bucket_value.py --target data/swaps_v3_030_25785425_25799780.csv \
                        --fast   data/swaps_v3_001_25785425_25799780.csv \
                        --deep   data/swaps_v3_005_25785425_25799780.csv

# §9
python3 manipulation_cost.py --csv data/swaps_v3_001_25785425_25799780.csv
```

`discover.py` resolves pool addresses from the v3 factory. `find_blocks.py`
binary-searches block numbers for a UTC date range. `fetch.py` pulls swap events and
candles. Outputs land in `out/` and are committed, so every table above can be diffed
against a fresh run.
